# Security

Sequo API handles personal data, delivery addresses, wallet transactions, merchant finances, and admin operations. Security must be built into authentication, authorization, provider callbacks, financial ledgers, audit logs, and operational tooling.

## Security Principles

- Treat every client request as untrusted.
- Enforce authorization in the backend even if clients hide actions.
- Store no production secrets in Git or Markdown.
- Use HTTPS-only outside local development.
- Store money movements in append-only ledgers.
- Mask sensitive phone/address data by role and workflow need.
- Make wallet provider callbacks authenticated and idempotent.
- Audit every sensitive admin, financial, security, support, and settlement action.

## Authentication

Recommended model:

- Short-lived JWT access tokens.
- Opaque refresh tokens.
- Refresh token hashes stored in the database.
- Refresh token rotation on every refresh.
- Refresh token reuse detection revokes the session family.
- Logout revokes server-side refresh session.
- Account lock revokes all active sessions.

JWT claims:

| Claim | Purpose |
| --- | --- |
| `iss` | Issuer |
| `aud` | Audience |
| `sub` | User ID |
| `exp` | Expiration |
| `iat` | Issued at |
| `jti` | Token ID |
| `roles` | Role list generated by backend |
| `session_id` | Optional session reference |

## Authorization

Authorization is role plus ownership.

Examples:

- Customer can read only their own orders.
- Merchant can read only their own merchant/sub-order/payout records.
- Merchant staff can perform only granted merchant-scoped actions.
- Courier can access only assigned or offered missions.
- Relay partner can access only parcels at their assigned Point de Relai.
- Support access is limited and audited.
- Finance/admin actions require admin or finance-specific permission.

## Sensitive Actions Requiring Audit

- Login failure spikes, refresh reuse, account lock.
- Role or permission changes.
- Merchant KYC approval or suspension.
- Merchant commission changes.
- Product base price or platform margin changes.
- Bargaining acceptance and price lock creation.
- Payment webhook accepted or rejected.
- Refund approval or rejection.
- Physical return receipt.
- Payout batch creation, approval, send, failure.
- Admin override of order/delivery/return/settlement state.

Audit logs must avoid raw tokens, wallet secrets, passwords, and full provider payloads containing secrets.

## PII Protection

Protected fields:

- Phone numbers.
- Delivery addresses.
- Landmarks and notes.
- GPS coordinates.
- KYC documents.
- Wallet account references.
- Support evidence photos.

Rules:

- Mask phone numbers unless the workflow requires contact.
- Prefer masked call/SMS/WhatsApp routing when possible.
- Do not expose full customer history to merchants or couriers.
- Do not expose one cooperative member's financial data to other members.
- Restrict KYC documents to authorized admin workflows.
- Log only redacted address/payment data.

## Wallet Security

Supported current provider scope:

- Yas Togo.
- Moov Africa.

Required controls:

- Verify webhook signatures.
- Verify provider event timestamps where available.
- Use idempotency keys for provider callbacks.
- Store provider references and callback hashes.
- Reject duplicate terminal events that conflict with stored payment state.
- Reconcile provider transaction lists against internal ledger.
- Alert on invalid signatures, replay attempts, and amount mismatches.

No cash withdrawal operations should be implemented.

## Idempotency

Idempotency is required for:

- Checkout creation.
- Payment intent creation.
- Wallet callbacks.
- Order creation after payment.
- Refund trigger.
- Return physical receipt.
- Payout batch creation and approval.
- Bargaining acceptance.

Reuse of the same idempotency key with a different request hash must return a conflict.

## Financial Integrity

Rules:

- Do not mutate historical ledger entries.
- Correct mistakes with reversing or adjustment entries.
- Paid order snapshots are immutable.
- Commission rate snapshot is stored on merchant sub-order.
- Platform margin snapshot is stored on order item.
- Refund responsibility is explicit.
- Payout batches keep source order/ledger references.

## PIN Security

Delivery and return PINs:

- Are generated server-side.
- Are short-lived.
- Are single-use.
- Are stored hashed.
- Track failed attempt count.
- Are invalidated after successful use.

Never store plaintext PIN beyond the immediate response/notification step.

## Secrets

Secrets include:

- JWT signing keys.
- Database credentials.
- Yas/Moov provider credentials.
- Webhook secrets.
- SMS/push/WhatsApp keys.
- Object storage credentials.
- Admin bootstrap passwords.

Rules:

- Local development can use uncommitted environment files.
- Staging and production must use deployment secret manager.
- Rotate provider credentials after suspected leakage.
- Never put real secrets in docs, screenshots, fixtures, or tests.

## Rate Limiting

Current implementation:

- Auth endpoints use `AuthRateLimiter`, an in-memory fixed-window limiter.
- Signup, login, social login, refresh, forgot-password, and reset-password are limited by client IP fingerprint plus a safe subject key where possible.
- Blocked auth requests return `429` and `Retry-After`.
- Raw emails, reset tokens, refresh tokens, and IP addresses are not stored as limiter keys; the limiter uses hashes/fingerprints.

Rate limit:

- Login. First-pass in-memory limit implemented.
- Refresh. First-pass in-memory limit implemented.
- Signup. First-pass in-memory limit implemented.
- Social login. First-pass in-memory limit implemented.
- Password reset and forgot-password. First-pass in-memory limit implemented.
- OTP if implemented later.
- Bargaining offers.
- Checkout and payment intent creation.
- Wallet webhook endpoints by provider/IP/signature context.
- Return request creation.
- Admin high-risk actions.

Production hardening still required:

- Add gateway-level or Redis-backed distributed limits before running multiple API instances.
- Add persistent failed-attempt counters, progressive delay or account lockout, and audit events.
- Add provider-specific webhook limits that combine IP, signature validity, and provider reference context.

## Startup Guardrails

Current implementation:

- Production-like profiles (`docker`, `prod`, `production`, `stage`, `staging`) fail startup when development defaults are still active.
- Guardrails cover JWT signing secret, notification token encryption secret, Google/Facebook/Apple placeholder IDs, Yas/Moov wallet secrets, explicit HTTPS CORS origins, tracked placeholder/test/local markers, H2 usage, H2 console, and unsafe Hibernate DDL modes.
- Local Docker Compose and CI explicitly opt into development defaults with `SEQUO_ALLOW_DEV_DEFAULTS=true`; named `prod`, `production`, `stage`, and `staging` profiles still enforce strict checks even if that flag is set.

## Operational Alerts

Alert on:

- Invalid wallet webhook signatures.
- Payment amount mismatch.
- Multiple failed PIN attempts.
- Refresh token reuse.
- Spike in failed logins.
- Payout provider failures.
- Refunds stuck after physical receipt.
- Orders stuck in paid but not merchant-pending.
- Delivery shortfalls above configured threshold.
- Relay parcels stuck beyond policy.

## Required Security Tests

- JWT issuer/audience/signature/expiry validation.
- Refresh rotation and reuse detection.
- Role and ownership checks.
- Merchant cannot access another merchant's order.
- Courier cannot access unassigned mission.
- Relay cannot receive parcel for another relay unless admin flow.
- Invalid wallet signature rejected.
- Duplicate webhook idempotent.
- Paid order snapshot immutable.
- Ledger correction uses adjustment entry.
- Audit log emitted for commission, refund, payout, and role changes.

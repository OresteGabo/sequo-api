# Requirements

This file tracks API-related requirements extracted from the latest owner interview notes and reconciles them with the current Spring Boot backend implementation.

Detailed delivery and fulfillment coverage is tracked in [DELIVERY.md](DELIVERY.md).

## Verified MVP Launch Priorities

Audited on 2026-09-11 against the current Spring Boot code and tests, not just the checklist state.

1. **Payment finality:** real Yas Togo and Moov Africa payment adapters, webhook-to-order reconciliation, and production credentials are still launch blockers for any paid MVP. The runtime processor intentionally returns `Pending`, so `/api/orders/process` cannot complete a real paid order without a provider integration or reconciliation path.
2. **Authorization hardening:** persisted user roles, merchant membership scopes, merchant-scoped financial/fulfillment reads, and owner-checked customer delivery tracking are now wired through JWT/WebSocket auth. Remaining pre-MVP hardening is relay-point ownership, app-family/device-token role scoping, admin role-management APIs, and a sweep of any newer controllers for ownership checks.
3. **Checkout financial snapshot:** accepted orders persist item subtotal, delivery fee, total, payment refs, order lines, and merchant sub-orders, but not the full quote audit trail. Before launch, persist quote version, base price, platform margin, service fees, distance source/meters, courier estimate, final shortfall estimate, and any bargaining lock consumed at checkout.
4. **Notification provider delivery:** in-app inbox, outbox, routing, WebSocket/STOMP, preferences, and delivery-attempt audit exist. Real Firebase Admin and SMS adapters are still required if MVP promises push/SMS outside the app.
5. **Production worker configuration:** startup guardrails exist, but schedulers are opt-in. Before launch, enable and verify the outbox worker, provider-delivery retry worker, relay delay scanner, mission expiry scanner, dispatch scanner, settlement eligibility scanner, refresh cleanup, and device-token pruning in the deployed environment.
6. **Payout execution:** merchant payout accrual, eligibility promotion, ledger reads, relay fee deltas, and delivery shortfall ledger posting exist. Provider payout execution, payout sent/paid/failed reconciliation, and operational approval flows remain outside the implemented backend.

## Status Legend

- `[x] Implemented`: domain code exists and has focused tests.
- `[ ] MVP-safe`: current behavior is acceptable for an MVP launch under documented manual-ops or provider-depth constraints.
- `[ ] Partial`: documented or partly modeled, but missing persistence, controller, integration, scheduler, or full workflow.
- `[ ] Not implemented`: no meaningful backend implementation yet.
- `[ ] Decision needed`: owner/product decision is still needed before implementation.

## Immediate Implementation Backlog

- [x] Production startup guardrails for missing JWT secrets, notification token encryption secrets, OAuth placeholders, wallet secrets, explicit CORS origins, and unsafe database configuration.
- [x] Safer default runtime config: Flyway owns schema creation, Hibernate validates mappings, and H2 console is disabled unless explicitly enabled for local development.
- [x] First-pass in-memory auth rate limiting for signup, login, social login, refresh, forgot-password, and reset-password endpoints.
- [x] General in-memory leaky-bucket protection for non-authenticated API traffic, with safe `429` and `Retry-After` responses.
- [x] Placeholder replacement tracker and production readiness check for fake URLs, provider IDs, local defaults, and test-only secrets.
- [ ] Distributed/gateway rate limiting for multi-instance production and future OTP endpoints.
- [ ] RBAC plus ownership checks for merchant, relay, courier, admin, and customer resources. `AuthorizationPolicy` centralizes role, ownership, merchant-scope, assignment, and financial-access decisions; persisted user roles and active merchant memberships now flow through JWT/WebSocket auth; merchant fulfillment, consolidation, settlement, delivery mission, relay, customer tracking, support, and admin monitoring controllers integrate role/scope checks.

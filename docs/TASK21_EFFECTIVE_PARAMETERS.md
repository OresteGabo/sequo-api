# Effective SEQUO business parameters

The signed contract, Annex A.6, page 13, references 131–140, permits values to be modifiable by SEQUO or technically prepared for modification. This implementation uses the existing settings, policies and authenticated reads. It does not introduce a second configuration store.

ADMIN and SUPER_ADMIN can read `/api/admin/web/business-parameters` and Settings in sequo-admin. The response retains earlier fields and adds ten `parameters` entries, with live values, configuration/approval state, runtime source, change authority, procedure and verification. A configured or active seed is not proof of SEQUO approval. The response reads an explicit allowlist; it never serializes environment variables or credential-bearing service objects.

| Contract | Effective source | Authorized change and verification |
|---|---|---|
| 131 Minimum delivery price | `DeliveryPricingService.effectiveRecord()`, otherwise `DefaultSettings` | SEQUO authorizes a controlled `delivery_pricing_settings` profile change. `active` and `effective_from` determine applicability; future rows do not apply early. Read `/api/admin/web/delivery-pricing` and quote below/at/above the included distance. |
| 132 Extra kilometer price | The same effective pricing record; whole-kilometer ceiling in the pricing engine | Change the approved `extra_km_fee_cfa`/`included_km` settings with 131. Verify authoritative quotes and persisted checkout pricing; client totals/distance never select the tariff. |
| 133 Merchant commissions | `MerchantCommissionConfigurationService`: override first, otherwise `MerchantCommissionPolicy` | ADMIN/SUPER_ADMIN uses `PUT /api/commissions/merchant-overrides/{merchantId}` with `commissionRateBps` and reason; `DELETE` restores the runtime default. Default/range changes require a reviewed deployment. Read the merchant rate and a new sub-order snapshot; preserve older order rates. |
| 134 Subscriber rates | Persisted plan rates, monthly cap, approval reference and loyalty fields, applied by `DeliveryBenefitsService` | SEQUO approves the complete plan; a privileged operations change records the approved plan. Customer activation separately requires verified payment, period dates and activation reference. Loyalty remains disabled without an approved written rule and verified continuous paid tenure; `startedAt` alone is insufficient. The existing 30-day month calculation is not a new production policy approval. Read public `/api/subscriptions/plans`, owner `/api/subscriptions/benefits`, and cart quote; test pending/expired activation, caps and once-only paid consumption. |
| 135 Referral credits | `ReferralAwardPolicy`, approved persisted credit and remaining balance, checkout benefit reservation/application | Deployment configuration is `sequo.referrals.credit-cfa`, `approval-reference`, `expiry-days`. Zero amount or missing approval disables new awards. RESERVED/legacy unapproved credits do not discount checkout; operator approval of an issued credit is separate. Existing approved credits retain their own amount/expiry/remaining balance. Owner benefits and quote verify delivery-only use, expiry and paid consumption. No cash withdrawal or provider payment is implied. |
| 136 Bargaining attempts | `PersistedBargainingService` and its configured `BargainingPolicy` | Change `BARGAINING_MAX_CUSTOMER_ATTEMPTS` / `BARGAINING_MAX_MERCHANT_ATTEMPTS` in authorized deployment configuration, restart and verify thread maximum/used fields. Supported history across the same parties/product retains its attempt budget; a new thread does not reset it. |
| 137 Price lock duration | `BARGAINING_ACCEPTED_PRICE_LOCK_HOURS`; each accepted thread persists its own expiry | Approved deployment changes affect new agreements. Existing stored expiry is retained unless SEQUO approves a separate migration. Verify acceptance/expiry readback and basket/checkout just before and at expiry. |
| 138 Return request window | `CustomerReturnPolicy.window`, authoritative delivery/pickup time and server return clock | Change `RETURN_WINDOW_HOURS` under SEQUO change control and restart. Eligibility currently evaluates the configured window from persisted handoff, so decide the treatment of already-delivered orders before changing it. Never reset handoff timestamps to extend the window. Verify owner `/api/returns/orders/{orderId}/eligibility` before/at/after its deadline. |
| 139 Relay custody and fees | Live `RelayParcelPolicy`, parcel `feeStartsAt`, and each persisted assessment's daily rate | Configure approved ISO-8601 `sequo.relay.storage-fee-after` / `sequo.relay.review-after`. Fee eligibility is strictly after the threshold; review is at its threshold. `RELAY_DELAYED_PARCEL_SCHEDULER_ENABLED` schedules reviews only. A tariff is not invented: authorized manual assessment supplies an approved `dailyFeeCfa`; replay retains the old assessment rate. Missing legacy fee starts require an approved policy before any migration/charge. Disposition stays operator-controlled. |
| 140 Excluded categories | `RelayParcelPolicy`, persisted checkout category with supported legacy fallback, and `CustomerReturnPolicy.excludedCategories` | Return exclusions use approved `RETURN_EXCLUDED_CATEGORIES`. Relay exclusions are centralized typed rules prepared for reviewed extension/configuration. Check food/grocery, perishables, sensitive/pharmacy and general goods in checkout, rerouting and returns together. Empty return exclusions do not create a blanket food-return ban. Click-and-collect routing remains a separate SEQUO decision. |

The read-only inventory does not approve tariffs, subscriber rates, referral amounts, loyalty rules or migration policies. Use local/staging fixtures for change verification, then retain the approved business reference in the supported configuration/record. Do not put credentials in approval references, reasons or audit notes.

# SEQUO Admin Authentication Implementation Plan

This plan audits the current authentication surface before adding SEQUO Admin phone-approved login. It is based on the current API and app code, not proposed routes.

## Existing Backend Auth Surface

The API auth controller is `src/main/kotlin/dev/orestegabo/sequo_api/domain/auth/AuthController.kt`. It is currently mapped to both `/api/v1/auth` and `/api/auth`; new admin authentication work must use `/api` only while avoiding accidental regressions for existing clients.

Available auth flows today:

| Flow | Existing route | Notes |
| --- | --- | --- |
| Social login | `POST /api/auth/social/{provider}` | Supports `GOOGLE`, `FACEBOOK`, and `APPLE` through provider verifiers. Social users are provisioned as customers by default when no existing account exists. |
| WhatsApp OTP | `POST /api/auth/whatsapp/request`, `POST /api/auth/whatsapp/verify` | Uses an `AuthChallenge` with hashed code and 5-minute expiry. Current sender is a logging extension point. |
| Passkey registration | `POST /api/auth/passkey/register/challenge`, `POST /api/auth/passkey/register/finish` | Requires authenticated user. Current verifier is an extension point, not a complete production WebAuthn stack. |
| Passkey login | `POST /api/auth/passkey/authenticate/challenge`, `POST /api/auth/passkey/authenticate/finish` | Uses stored `UserIdentity` and challenge records. |
| Cross-device login | `POST /api/auth/cross-device/initiate`, `POST /api/auth/cross-device/resolve` | Existing phone/device approval flow is phone-number based and requires local biometric confirmation in the resolving request. It issues normal user tokens. |
| Refresh | `POST /api/auth/refresh` | Requires `refreshToken` and `deviceId`; refresh token is rotated by revoking the previous `UserDevice` session and issuing a new one. |
| Logout | `POST /api/auth/logout` | Revokes the refresh session matching the provided refresh token. |
| Logout all | `POST /api/auth/logout-all` | Revokes active refresh sessions for the authenticated user. |
| Sessions | `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{sessionId}` | Lists/revokes refresh sessions without exposing token hashes. |
| Current user | `GET /api/auth/me` | Returns safe profile fields including roles. |

## Token Model

`AuthService.issueTokensForUser` issues:

- JWT access token via `JwtService.generateAccessToken`.
- Opaque refresh token generated by `PasswordResetTokenService.generate()`.
- Refresh token hash stored on `UserDevice.refreshTokenHash`.
- Session metadata stored on `UserDevice`: `deviceId`, `appSource`, `fcmToken`, `expiresAt`, `lastActiveAt`, `revokedAt`.

`JwtService` stores role information, merchant scopes, provider, email, and session id in the JWT session model. Protected routes use `Authorization: Bearer <accessToken>`.

Refresh tokens are rotated: `refreshTokens` finds the hashed refresh token, validates device id, revokes the old device session, then issues a replacement token for the same device id/app source.

## Roles And Authorization

Roles are defined in `AuthModels.kt`:

- `CUSTOMER`
- `MERCHANT_OWNER`
- `MERCHANT_STAFF`
- `COURIER`
- `RELAY_PARTNER`
- `SUPPORT_AGENT`
- `ADMIN`
- `SUPER_ADMIN`

Useful role groups are defined in `RoleAuthorities.kt`:

- `RoleGroups.AdminOnly = ADMIN, SUPER_ADMIN`
- `RoleGroups.AdminOperations = SUPPORT_AGENT, ADMIN, SUPER_ADMIN`
- `RoleGroups.MerchantOperators = MERCHANT_OWNER, MERCHANT_STAFF, ADMIN, SUPER_ADMIN`

`AuthorizationPolicy` allows `SUPER_ADMIN` broadly, allows `ADMIN` for non-delete operational actions, and allows `SUPPORT_AGENT` to read administrative monitoring operations.

## Existing Rate Limiting And Safety Patterns

`AuthRateLimiter` already protects social login, WhatsApp OTP, passkey, cross-device, and refresh flows. New admin auth endpoints should reuse this pattern or add named buckets for:

- admin login request creation by email and request origin
- admin login exchange attempts by request id/email/origin
- email OTP request/verify fallback

Existing code avoids returning provider raw failure details in most flows, although Google rejection currently returns structured diagnostic fields intended for client handling. New admin UI must map all failures to staff-safe copy.

## Existing Cross-Device Flow Reuse

The current `CROSS_DEVICE_LOGIN` challenge is close to the desired phone-approved admin login, but not sufficient by itself:

- It is phone-number based, while the admin web proposal starts from work email.
- It targets a requesting `DeviceBinding`, while the admin web needs a browser session request with a human-readable code.
- It issues normal tokens when resolved, while admin web should require admin/staff role before exchange.
- It does not expose a mobile list of pending admin web requests by email/account.
- It does not include the web-style status lifecycle: `PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`, `CONSUMED`.

The new implementation can reuse these ideas:

- `AuthChallenge`-style expiring challenge records, or a dedicated entity if clearer.
- `PasswordResetTokenService.hash`/`matches` for code verification.
- `AuthRateLimiter` pattern.
- `issueTokensForUser` for final token issuance after approval and code exchange.
- push notification extension patterns.

## Current App Auth Surfaces

Observed project docs/source indicate:

- Customer app `Sequo` and vendor app `SequoVendor` already use backend auth and Google/Apple concepts from the shared backend.
- `SequoVendor` has a production-style auth/network layer with secure token storage and refresh retry behavior from earlier work.
- `SequoRider` and `SequoHub` must be inspected before adding mobile approval UI because their implementation maturity may differ.
- `sequo-admin` currently has a temporary staff access key/demo mode UI and calls `/api/auth/me`, refresh, logout, and admin read surfaces directly.

## What Needs To Be Added

Phone-approved admin login needs new backend contract and implementation:

1. Admin web creates a login request with work email and browser/device label.
2. Backend returns request id, short code, expiry, and polling interval.
3. Admin web polls safe status only.
4. Logged-in eligible mobile users see pending requests for their account.
5. Mobile user approves or rejects.
6. Admin web exchanges approved request plus code for normal auth tokens.
7. Request becomes consumed and cannot be reused.
8. Audit and rate limiting cover every step.

Email OTP fallback needs a separate contract and implementation after phone approval works.

Optional social login can reuse existing social verification, but admin web must verify roles after login and clear the session if the user is not admin/staff.

Passkeys already have backend scaffolding but should be treated as a later/admin-hardening feature unless a complete production WebAuthn implementation is added.

## What Must Not Change

- Do not break existing mobile social login, WhatsApp OTP, passkey, refresh, or logout behavior.
- Do not remove existing route compatibility without a migration plan.
- Do not log or expose access tokens, refresh tokens, OAuth tokens, one-time codes, device tokens, or token hashes.
- Do not make Google/Apple the only admin login path.
- Do not display API route names or developer wording in the admin web UI.
- Do not allow ordinary customer/merchant/rider roles to approve admin web login unless they also hold an admin/staff role explicitly allowed by policy.

## Recommended Implementation Order

1. Document the admin phone login contract.
2. Add dedicated request model/status/repository.
3. Add secure human-readable code generation and verification.
4. Add request creation and polling endpoints.
5. Add mobile list/approve/reject endpoints with role checks.
6. Add web exchange endpoint and one-time consumption.
7. Update admin web login UI to use phone approval.
8. Add mobile approval screens in each relevant app.
9. Add email OTP fallback.
10. Revisit optional social login and passkeys behind clear config.
